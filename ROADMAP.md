# Roadmap — Copo d'Água

## Forma de trabalhar

Desenvolvemos **um módulo de cada vez**, nunca em paralelo, seguindo sempre a mesma sequência: Objetivo → Funcionalidades → Regras de negócio → Fluxo → Wireframe → Componentes UI → Modelo de dados → API → Estados → Validações → Casos limite → Critérios de aceitação → Testes → Backlog técnico → Melhorias futuras.

## Nota de terminologia

"Parceiro" é usado no produto com **dois significados distintos**, uma decisão consciente tomada a 2026-08-14 ao renomear "Fornecedor" para "Parceiro":

1. **Parceiro = a pessoa com quem o utilizador casa** (`Wedding.partnerName1`/`partnerName2`, passo de onboarding "Sobre o/a parceiro/a"). Este uso já existia antes e está documentado e testado em `mobile-app/onboarding/` e `mobile-app/wedding/`.
2. **Parceiro = prestador de serviços no marketplace** (`UserRole.partner`, `partner-app/`, `partner_profiles`). Este é o novo uso, que substituiu "Fornecedor".

A ambiguidade foi assumida deliberadamente (ver conversa de 2026-08-14) em vez de reverter ou escolher outro termo. Ao escrever UI copy ou documentação nova, desambiguar pelo contexto imediato ("o teu parceiro/a" vs. "parceiros no Marketplace") e evitar frases onde os dois sentidos possam colidir na mesma frase.

### Nota de arquiteto — especificação de admin panel avaliada e reduzida de âmbito (2026-08-30)

Foi recebida uma especificação ampla de "Admin Dashboard" (dashboard com KPIs, gestão de casais/reservas/pagamentos, disputas, reviews, categorias, comissões, analytics de funil, RBAC de 5 roles — `SUPER_ADMIN`/`ADMIN`/`SUPPORT`/`FINANCE`/`MODERATOR` —, definições de plataforma, paleta de cores própria). Implementado apenas o que o projeto já tinha identificado como bloqueador real: `admin-web/partners/` MVP (ver acima) e `docs/architecture/RLS_POLICY.md`. ### Atualização 2026-08-30 (noite) — Fase 1: `mobile-app`/`partner-app` ligados à autenticação Supabase real

Pedido explícito do utilizador, corrigindo uma leitura anterior conservadora demasiado literal ("wire it up" tinha sido interpretado só como navegação): **ligar admin, casal e parceiro à mesma base de dados real**, não só a UI mock entre si. Antes de escrever qualquer código Flutter, o planeamento descobriu um bloqueio real e não documentado: `on-user-created`/`on-partner-created` (`backend/auth/api.md`, `partner-app/profile/api.md`) estavam **documentados havia várias sessões mas nunca implementados** — nenhuma migração criava a linha em `profiles` ao dar-se um signup real. Corrigido em `database/migrations/011_auth_provisioning.sql` (`handle_new_user()` + `submit_partner_profile_for_review()`), validado ao vivo contra a API REST do Supabase Auth (signup real, `profiles`/`partner_profiles`/`partner_verification` confirmados, utilizador de teste depois apagado) — ver `database/README.md`.

Implementado do lado Flutter: `supabase_flutter` adicionado (`pubspec.yaml`), `core/supabase/supabase_config.dart` (novo), `main.dart` inicializa o cliente antes de `runApp`. `core/auth/auth_controller.dart` reescrito para chamar `auth.signUp/signInWithPassword/signOut/resetPasswordForEmail` reais e ler `profiles`/`partner_profiles` de volta — a forma de `AuthState`/`AuthStatus` manteve-se igual de propósito, para nenhum dos ~15 ecrãs que já observam este provider precisar de mudar. `switchDemoAccount()` (trocava entre as duas contas de demonstração fixas sem password) foi removida — sem equivalente com contas reais, cada uma com a sua própria password; os três sítios que a chamavam (`AccountSwitcherBadge` em `gradient_mark.dart`, o menu duplicado em `partner_home_screen.dart`, o atalho "Ver como Parceiro" em `settings_screen.dart`) tiveram o item de menu correspondente removido, não substituído. `Profile.password` nunca é preenchido com a password real (decisão de segurança do plano aprovado) — fica sempre `''`.

Verificado com `flutter analyze` (0 problemas) e `flutter build web` (sucesso).

**Verificação (mais tarde, 2026-08-30) — confirmado por teste humano real:** o primeiro signup real de teste revelou dois problemas não previstos no plano original, ambos corrigidos antes de se dar como fechada esta fase:

1. **"não recebi o email"** — não era um problema de entrega: o email de teste usado já era a conta admin existente do projeto (`alves.rafael.ferraz@gmail.com`, criada antes desta sessão), já confirmada. O Supabase não avisa nem envia nada para um `signUp()` de um email já confirmado — devolve um "sucesso" com `identities: []`, para não permitir descobrir que emails já têm conta. `register()` não distinguia este caso e mostrava sempre "verifica o teu email". Corrigido: `register()` agora deteta `identities` vazio e mostra "Este email já está registado. Tenta entrar em vez disso.".
2. **"não foi possível criar a conta"** (com um email novo, ainda sem conta) — este era real: `over_email_send_rate_limit` (HTTP 429). O serviço de email por omissão do Supabase (sem SMTP próprio configurado) tem um limite muito baixo, esgotado pelos testes desta sessão (verificação da migração 011, os dois diagnósticos acima). `register()` não mapeava este código para nada específico, caindo na mensagem genérica. Corrigido: mensagem própria ("Muitos pedidos de email em pouco tempo...").

**Decisão tomada com o utilizador:** em vez de esperar o limite resetar, "Confirm email" foi desligado nas definições do projeto Supabase (Dashboard → Authentication → Sign In/Providers → Email) — o utilizador fez esta alteração diretamente, não eu (não há forma segura e isolada de o fazer via CLI: `supabase config push` exigiria construir um `config.toml` do zero e empurrá-lo por inteiro para o projeto remoto, arriscando substituir outras definições que não consigo ler primeiro, já que não há `config pull`). Com a confirmação desligada, `signUp()` passou a devolver sessão ativa de imediato — `register()` foi ajustado para usar essa sessão quando presente (`response.session != null`) em vez de mostrar sempre o ecrã "verifica o teu email".

**⚠️ Ação pendente antes de produção real:** "Confirm email" está desligado como conveniência de teste, não como decisão de produto — `backend/auth/requirements.md` continua a assumir confirmação obrigatória. Voltar a ligar (e, idealmente, configurar SMTP próprio para não depender do limite baixo por omissão) antes de qualquer utilizador real se registar. Ver `backend/auth/tasks.md`.

Confirmado pelo utilizador: signup real através do preview web (`localhost:8092`) entra diretamente na app (onboarding para casal, dashboard para parceiro), sem passo de email. Fase 1 fechada — a avançar para a Fase 2 (Wedding).
