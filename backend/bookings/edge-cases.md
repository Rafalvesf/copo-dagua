# Bookings — Casos Limite

- `hold_expires_at` ultrapassado mas o cron ainda não correu (até 15 min de atraso) → a `booking` continua a aparecer como `awaiting_deposit` até ao próximo ciclo; `admin_confirm_deposit()` continua a funcionar normalmente nesse intervalo (não há verificação extra de "já devia ter expirado" na função — o `status` na base de dados é a única fonte de verdade, não um cálculo derivado de `hold_expires_at` em tempo real). Se isto se tornar um problema real (admin confirma um sinal 2 minutos antes do cron expirar), considerar verificar `hold_expires_at > now()` dentro de `admin_confirm_deposit()` — não implementado no MVP.
- Duas `bookings` `awaiting_deposit`/`confirmed` para o mesmo parceiro e a mesma `event_date`, criadas a partir de dois `quote_requests` diferentes → **corrigido 2026-09-12** (`056_prevent_partner_overbooking.sql`, errcode corrigido em `057_fix_overbooking_errcode.sql`) — `accept_proposal()` verifica explicitamente e recusa com `partner_already_booked` (`P0007`); índice único parcial `bookings_partner_active_date_uniq` cobre a corrida real entre dois `accept_proposal()` concorrentes (a verificação `exists()` em si não tranca nada antes do `insert`). Ver `tasks.md`.
- `expire_overdue_bookings()` corre e não encontra nenhuma booking elegível → `update` afeta 0 linhas, o `insert ... select from expired` também não insere nada; sem erro, sem-op silencioso, como esperado de um cron job.
- Admin chama `admin_complete_booking()` numa booking com `event_date` no futuro → permitido, sem verificação de que a data já passou; a decisão de "quando" marcar como concluída fica ao critério do admin (ex: o casal pode confirmar informalmente antes do dia). Documentado como decisão consciente, não como omissão.
