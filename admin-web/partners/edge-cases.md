# Partners (admin-web) — Casos Limite

- Dois admins abrem o mesmo perfil `pending_review` ao mesmo tempo; ambos clicam em decidir (um aprova, outro rejeita) → a segunda chamada falha com `invalid_state` (a pré-condição `status = 'pending_review'` já não é verdadeira depois da primeira). A UI mostra "Este perfil já foi decidido por outro administrador" e recarrega o estado atual — nunca assume que a sua própria ação teve sucesso sem confirmação do servidor (ver `state.md`).
- Admin abre o ecrã de detalhe, demora vários minutos a decidir (ex: a verificar o NIF externamente), e o parceiro entretanto edita um campo não-crítico → sem efeito no fluxo de decisão (campos não-críticos não mudam `status`, RN08 de `partner-app/profile/requirements.md`); a decisão do admin continua válida quando submetida.
- Admin tenta rejeitar um perfil que, entre carregar o ecrã e submeter, já foi editado pelo parceiro para `pending_review` novamente por causa de uma edição crítica noutra sessão → mesmo tratamento que o caso de dois admins: `invalid_state` só se o `status` inicial pressuposto pela Edge Function já não bater certo; se ainda for `pending_review` (só que "outra ronda"), a rejeição procede normalmente — o admin está a decidir sobre o estado atual, não sobre um snapshot antigo.
- Perfil é suspenso, mas entretanto a conta do parceiro (`profiles.status`) já estava suspensa por outro motivo (Authentication, RN08) → `is_partner_profile_visible()` já garantia que o perfil não aparecia no Marketplace antes desta ação; suspender o `partner_profiles.status` é redundante nesse caso mas inofensivo — não é um erro, só não muda a visibilidade efetiva (já estava invisível).
- Motivo de rejeição/suspensão contém dados sensíveis escritos por engano pelo admin (ex: cola acidentalmente um NIF ou nota interna) → `rejection_reason` é visível ao parceiro por design (RN07 de `partner-app/profile/requirements.md`); não há sanitização automática. Documentado como risco de processo, não de sistema — a mitigar com formação, não código, no MVP (ver `tasks.md` para uma eventual confirmação "este texto vai ser visível ao parceiro" antes de submeter).
- Lista de `pending_review` está vazia → estado vazio explícito ("Sem parceiros a aguardar revisão"), não um ecrã em branco nem um erro.
- Admin perde ligação a meio de uma chamada de Edge Function (ex: fecha o portátil) → a transação ou committa por completo (status + audit_logs) ou não committa nada; nunca um estado parcial (mudança de status sem registo de auditoria), porque ambos vivem na mesma transação SQL dentro da função (ver `database.md`).
